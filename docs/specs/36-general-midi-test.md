## 1. Summary
Two generic MIDI tests for documented MIDI connections: **MIDI conformance** (does the device send valid MIDI 1.0 while its MIDI controls are exercised, with an optional universal Identity Request) and **General MIDI sound check** (for devices with a General MIDI sound source: GM System On, program, drum map, volume/pan, pitch bend, polyphony, All Notes Off).

## 2. MIDI conformance (`midi:conformance`)
### 2.1 Active probe
When an output is selected, send Universal Device Inquiry `F0 7E 7F 06 01 F7` (device id 7F = all). Selecting an output requires a documented receiving connection; passive stream validation can run with no output. Generated DIN/unknown-transport conformance requires explicit output selection as described in §5. A valid reply is `F0 7E <id> 06 02 <mfr 1|3 bytes> <family 2> <member 2> <version 4> F7`. Parse manufacturer id (1 byte, or `00 xx yy`), family, member, version. The manufacturer *name* is not looked up (no verified registry bundled): hex is shown with a pointer to the MIDI Association SysEx ID list. No reply within 1.5 s is an **informational** finding, not a failure (many DJ controllers ignore it): `midi_identity_reply` = 0/1. The measurement is recorded only when the request was sent and either answered or its window closed: with no output port, a failed send, or Finish inside the window, no value is saved (an unasked question is not a "no").
### 2.2 Passive stream validation (user exercises controls for ~15 s)
Each received message (`bytes`) is checked:
- status byte valid (≥ 0x80, not undefined 0xF4/0xF5/0xF9/0xFD); data bytes < 0x80; length matches the status (note/CC/pitch bend = 3; program/channel pressure = 2; poly pressure = 3; song position 3; song select/time code 2; real-time 1) → `midi_invalid_messages`.
- SysEx: starts `F0`, ends `F7`, all inner bytes < 0x80 → `midi_sysex_malformed`.
- Note pairing: note-off (or note-on velocity 0) without a captured note-on → `midi_orphan_note_offs`; notes without a captured release at session end → `midi_stuck_notes`. All Notes Off (CC123, value 0) and the note-release part of mode changes CC124–127 release the addressed channel's pending notes. Later individual note-offs for those same observed notes are accepted once each. All Sound Off (CC120) silences a receiver without supplying key-release messages; controller reset, Local Control and sustain changes likewise do not clear the pairing ledger. These metrics describe captured messages, not physical sound, pedal-held voices or switch faults. Channel-mode semantics follow the [MIDI Association message summary](https://midi.org/summary-of-midi-1-0-messages).
- 14-bit CC pairs (CC n and n+32 on one channel, n 0–31) where more than 50 % of the halves have no partner within 20 ms → `midi_unpaired_14bit` count of such controllers (informational flag, not failure).
- Active Sensing (`FE`): if seen, maximum gap must be ≤ 330 ms (spec 300 ms + tolerance) → `midi_active_sensing_gap_ms`.
- MIDI Clock (`F8`): if seen, coefficient of variation of intervals → `midi_clock_jitter_percent`.
- Channels used, message-kind histogram, burst rate (peak messages per 100 ms window; informational in `extra`).

Active Sensing and Clock numerics require finite, nonnegative timestamps in captured arrival order. Backwards times are not sorted or coerced into measurements. Equal times remain valid batched arrivals, but Clock needs at least eight ticks with a positive span; zero-span or unrepresentable timing remains unavailable. A supplied Active Sensing session end must be finite and no earlier than its last message. Clock variation is calculated from normalized intervals to avoid overflowing their squares.

When the runner marks transport timing unavailable, it passes `timingObserved: false` to the analyzer. Packet counts, bytes, channels and note-release evidence remain available. Active Sensing, Clock, 14-bit pairing and burst-rate numerics are omitted or explicitly `null`; host receipt timestamps cannot substitute for transport measurements. The existing capture-integrity finding and REVIEW result remain authoritative. These host timestamp checks do not establish physical timing accuracy.

Pass: `midi_invalid_messages equals 0`, `midi_sysex_malformed equals 0`, `midi_stuck_notes equals 0`; orphans are a warning (result REVIEW). Evidence rules in the panel: no messages, no channel (control) messages, a full capture (100,000 messages) or host-side MIDI queue drops during the capture window give REVIEW because dropped or unseen messages can look like stuck or orphan notes.

The panel observes `midi.status()` at capture start and Finish. A loss delta requires non-negative safe-integer `dropped` counters at both observations with no decrease; missing/invalid counters are `unavailable`, a decrease is `reset`, and both give REVIEW with a `null` delta. Web MIDI has no measured host-loss counter, so the bridge's compatibility zero cannot establish zero loss. The selected input must appear in both `openInputs` observations; a missing input or unavailable input status gives REVIEW. Saved `extra.captureIntegrity` retains counter state, before/after counts, input observations and `counterScope: 'all-inputs'`. This shared counter does not attribute loss to one device, and two name-based snapshots do not prove uninterrupted physical connection.

## 3. General MIDI sound check (`midi:gm`)
Requires an output port. Only auto-added when `profile.midi.generalMidi === true`; runnable on any device via manual start. GM Level 1 facts used (sources: General MIDI, Wikipedia; MIDI Association specification): GM System On `F0 7E 7F 09 01 F7`; 16 channels, channel 10 is percussion, percussion key map notes 35–81; 128 melodic programs; minimum 24 simultaneous voices (or 16 melodic + 8 percussive); required controllers CC1, 7, 10, 11, 64, 121, 123; default pitch-bend range ±2 semitones; Master Volume `F0 7F 7F 04 01 ll mm F7`.
Step list (each plays audible notes; user answers Yes/No; DeckChek builds exact bytes via `gmSteps()`): 1 System On + reset (CC121) → middle C on program 0 (Acoustic Grand Piano); 2 program sweep (0, 24, 40, 56, 73, 80 on ch1); 3 percussion ch10 notes 35, 38, 42, 46, 49, 51; 4 CC7 volume fade 127→20; 5 CC10 pan hard left→right; 6 pitch-bend up then down; 7 sustain CC64 on/off with a chord; 8 polyphony burst: 24 simultaneous notes across ch1 and ch10 (spec voice count); 9 All Notes Off (CC123) while 6 notes hold → silence expected; 10 Master Volume SysEx half level.
Result: `midi_gm_ok_percent` = Yes ÷ answered ×100; each No becomes a finding naming the feature; pass default `>= 100` (a GM device must support all), steps may be marked N/A.

## 4. Acceptance criteria
- AC-1 `validateMessage` flags every malformed class above and accepts all valid channel/system messages.
- AC-2 `analyzeStream` over a clean synthetic session reports zeros; over crafted sessions reports exact orphan, stuck, malformed-SysEx, active-sensing-gap and clock-jitter values.
- AC-3 `parseIdentityReply` decodes 1-byte and 3-byte manufacturer ids and rejects short/wrong frames.
- AC-4 `gmSteps()` bytes match the GM facts in §3 (System On bytes, ch10 = status 0x99, notes within 35–81, 24-note polyphony, CC121/123/7/10/64 numbers).
- AC-5 No MIDI backend / no ports / no output port → clear empty state, test can be skipped, no crash.
- AC-6 FS-34 conditional MIDI prerequisites appear in the runner instructions; direct Skip remains available without a backend/input, records an unestablished prerequisite rather than a negative hardware claim, and retires only that run's owned connection. Generated DIN/unknown conformance starts listen-only, including with a sole host input/output pair; explicit output selection enables the existing probe.

## 5. Connection ownership (UI)
Each panel is built for one connection (input claim + output selection captured at build time) and is disposed on refresh, port change or leaving the screen. Conformance: the Identity Request, its 1.5 s timer and Finish (including its await of the drop counter) check that connection before every state change and save. GM: every send goes through one per-panel queue on the captured output selection, so the abort cleanup (`gmAbortCleanup()`: sustain off, All Notes Off and All Sound Off on 16 channels, then pitch bend centre, CC7 100, CC10 64 and full master volume) is queued behind any in-flight note and never follows a replacement UI selection; stopping, failing, saving or disposing mid-step aborts the step. Logical endpoint selection and its remaining physical-identity limits are described in §7. Regression tests: `tests/midi-fs36-ui.test.mjs`.

Input and output selectors make the pairing visible. For handwritten tests and generated tests with confirmed USB MIDI, an automatic output choice requires an unambiguous exact name/profile match or the sole input/output pair; changing the input recomputes that choice. A matching host name alone does not establish the tested device's physical identity or receiving capability.

FS-34 generated conformance tests whose USB MIDI transport is unconfirmed carry `params.outputSelection: 'explicit'`. This covers documented DIN and unknown transport without inferring DIN input direction. For these generated tests, initial mount, input change and refresh leave the output unselected even when names match or a sole pair exists. The operator must select a documented receiving path before the existing Identity Request can send; passive capture remains available. The policy is limited to `auto: true` conformance tests carrying that parameter. Shared prerequisite guidance describes documented device DIN OUT → interface IN or an unresolved connection, without assuming direct device USB.

A manual output change rebuilds the connection, so its panel retains its own captured output and cleanup ownership. A name-only selector still requires a unique name. Distinct logical IDs make duplicate-name inputs and outputs independently selectable, with ID labels that distinguish the options; duplicate names never establish an automatic output pair. Unavailable or colliding IDs stay unselectable. Conditional Skip uses the same disposal path as leaving the screen; stale opens, probe results and Finish callbacks cannot save afterward, and an input claimed by a replacement run is retained. A saved capture cannot subsequently be replaced by conditional Skip. Existing capture-evidence and GM rules remain unchanged.

## 7. Explicit logical endpoint selection

Enumeration now preserves the opaque endpoint ID exposed by the pinned native MIDI backend and by Web MIDI. Each port has `id`, `name` and display-order `index`; native `nameAvailable` distinguishes a failed name read from a successfully read empty label. Indices are not connection identities. The bridge accepts these selectors:

| Operation | Selector and scope |
| --- | --- |
| `open('name')` / `close('name')` | Legacy exact-name input selection or captured input alias. New opens require a unique, successfully read name. |
| `open({ id })` / `close({ id })` | One logical input ID. `close` is input-only. |
| `send({ id }, bytes)` | One logical output ID, captured on first send. |
| `send('name', bytes)` | Legacy unique-name output selection on first send; later sends retain its captured alias. |
| `closeAll()` | Explicit reset of both input and output connections and retained output bindings. |

An optional selector `backend` must match the active bridge. Connection keys include backend, direction and ID; an input and output with equal raw IDs remain separate owners. Equal IDs across directions do not establish an automatic pair. An explicit ID never falls back to a supplied display name or enumeration index. Missing, empty, malformed or colliding explicit IDs are rejected; the opaque string `"0"` is not globally rejected. A legacy enumeration without IDs remains usable only through unique-name selection. Native ID selection still requires a successful name read, including a successfully read empty name.

Messages retain the display name in `port` and add `portId`; status retains name arrays and adds `openInputIds` and `openOutputIds`. A selected ID's capture status is checked against the ID array. A matching display name cannot establish that the selected endpoint stayed open. Device results and learned-map metadata retain human-readable names and may include the observed logical ID and backend; they do not create an automatic binding across machines.

The Devices runner and Mapper Learn keep the selected ID across enumeration reorder. If that ID disappears, its unavailable selection remains visible and a replacement requires an explicit choice. Duplicate-name outputs require manual selection. Generated DIN/unknown-transport conformance retains its stricter explicit-output policy from §5.

Both consumers share one input-claim and close-barrier ledger. A canceled or disposed pending open cannot close a successor on the same logical input, including a transition between Mapper Learn and a device test. Mapper preserves an input that was already open before its own claim and refuses to infer ID ownership from name-only status. Input callbacks, late panel results and cleanup retain their captured endpoint. Legacy and ID selectors share the same connection and cancellation boundary. A vanished or failed output keeps a retired binding; Note Off cleanup cannot reconnect to another device with the same name. Existing captured cleanup does not re-enumerate an ambiguous name.

This completes logical routing in software, not physical-device qualification. The [Web MIDI ID specification](https://www.w3.org/TR/webmidi/#dom-midiport-id) requires unique IDs and recommends persistence while describing systems that cannot maintain completely persistent identifiers. Native IDs are backend-dependent and are treated as opaque. Neither establishes permanent physical identity, cross-machine equivalence, uninterrupted hot-plug continuity, or the identity of equipment behind a DIN interface. Full native/platform and physical MIDI/GM qualification remain separate gates; deterministic bridge, UI and native-body harness tests do not replace them.
